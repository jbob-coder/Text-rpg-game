# Conversation Context — Pixel-Art Generation / Extraction Directive

Recorded: 2026-10-03 AST  
Repository: `jbob-coder/Text-rpg-game`  
Program branch: `docs/master-game-development-program`

## Owner directive

The final game uses **pixel art** as its primary authored visual language.

The owner clarified that new visual material should be created through the ChatGPT-assisted project workflow itself. The intended production loop is not to depend on unrelated external asset packs as the game's visual foundation.

The assistant is expected to:

1. determine the visual asset requirements from the game/design documentation;
2. generate the required source/reference art for those requirements;
3. identify and extract the useful visual components from generated source boards or sheets;
4. reconstruct/clean those components into native-grid pixel-art production assets where required;
5. separate reusable pieces into sprites, tiles, props, portraits, overlays, FX, UI elements, equipment layers, map elements, and other documented asset families;
6. assign stable IDs, filenames, anchors, dimensions, palettes, transparency, reuse class, provenance, and state bindings;
7. integrate the resulting production assets into the game only after the relevant visual QA gates are satisfied.

## Important quality rule

"Generated by the assistant" does **not** mean that every generated image is automatically a runtime asset.

The existing repository rule remains useful:

- concept/reference generation may be larger or composition-oriented;
- anything entering production must satisfy the native pixel grid, palette, silhouette, transparency, layer, state-binding, and phone-scale requirements;
- generated sheets may be deliberately designed for extraction;
- extracted assets may require pixel reconstruction, cleanup, palette reduction, edge repair, anchor alignment, or re-authoring before promotion;
- the final production asset is the cleaned/native asset, not the mere existence of a generated reference.

## Target production chain

`documented game requirement -> assistant-generated source/reference -> asset extraction/decomposition -> native pixel reconstruction/cleanup -> metadata/provenance -> integration -> runtime/phone QA -> canon approval`

## Asset families expected from this workflow

Examples include:

- player and NPC sprites;
- character turnarounds;
- portraits and emotion variants;
- equipment/paper-doll layers;
- held objects;
- item icons;
- buildings and structural modules;
- environment tiles;
- props and landmarks;
- room/location scene art;
- map art and markers;
- state overlays;
- ability/status FX;
- animation frames;
- navigation/status/quest UI icons;
- panel frames and other pixel UI art.

## Documentation consequence

Every major area/system packet should explicitly state:

- what visual assets it needs;
- what source image/board should be generated;
- which production assets are extracted or reconstructed from it;
- native size/grid;
- layer/anchor requirements;
- reuse compatibility;
- consuming location/screen/system;
- authoritative state binding;
- QA and provenance status.

This directive supplements the existing pixel-art production standards and does not weaken their no-smoothing, native-grid, state-ownership, provenance, or QA requirements.
