# Documentation and Guide Scale Program

Status: ACTIVE / CAPACITY PLANNING

## Owner scale targets

The owner specified very large long-horizon targets, including thousands of documentation and guide/planning units and a very large final total corpus.

These targets are interpreted as:
- permission to decompose aggressively;
- expectation of deep coverage;
- expectation of long-term continuity;
- not a requirement to manufacture meaningless files.

## Documentation unit rule

A unit exists only when it has one clear ownership purpose.

Good unit:
- `REGION_NORTH_COAST_RESOURCE_ZONES.md`

Bad unit:
- splitting one coherent 2-page rule into 20 tiny files solely to increase count.

## Recommended hierarchy

### Tier 0 — Program control
Owner directives, master indexes, authority rules, handoffs.

### Tier 1 — Domain architecture
World, art, NPC/social, systems/combat, economy/ecology, Android.

### Tier 2 — Subsystems
Example: tactical combat, class system, map coordinates, panel system.

### Tier 3 — Content families
Regions, settlements, factions, beasts, item families, quests, UI surfaces.

### Tier 4 — Individual implementation/content records
Specific city, route, NPC, beast, item, scene, asset, test plan.

## Guide families

Guides should teach execution:
- how to add a settlement;
- how to add a region;
- how to add an NPC;
- how to add a beast;
- how to add an item;
- how to add a class;
- how to add an ability;
- how to add a quest;
- how to add pixel assets;
- how to create overlays;
- how to bind contextual panels;
- how to migrate save schema;
- how to add Android UI surfaces;
- how to verify builds;
- how to retire old code safely.

## Indexing requirement

Every document must be discoverable from an index by:
- domain;
- stable ID/name;
- status;
- authority/evidence class;
- dependencies;
- consumers.

## Anti-filler requirement

Do not mark the scale target as achieved through duplicated prose, generated boilerplate, or documents with no unique ownership.
