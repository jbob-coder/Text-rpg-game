# Reference Extraction Notes — My Vampire System

This document records only abstract game-design lessons extracted from the supplied reference material. It does not copy story text, character identities, setting names, proprietary terminology, or scene prose into the game.

## Mechanics worth abstracting

- A visible status model can make progression legible: level/experience, health, physical attributes, skills, and locked features that open later.
- Quests can provide directed progression while still allowing ordinary world activity.
- Powers become more interesting when they include drawbacks, resource costs, environmental disadvantages, prerequisites, and technique-specific limitations.
- Ability growth can be separated from raw combat strength. A formal ability rank can represent access/complexity while actual outcomes also depend on skills, tactics, equipment, and circumstances.
- Equipment can provide both numeric modifiers and unique active/passive effects.
- Crafting quality can depend on material quality and crafter technique rather than recipe identity alone.
- Power systems can expand into multiple energy/resource layers over time, but each layer needs a clear gameplay purpose to avoid redundant meters.
- Passive skills and major unlocks are effective rewards when they materially alter rules rather than only add larger numbers.
- Factions, leadership, social standing, and information can affect the same progression loop as combat.

## What this project changes

- Original setting, terminology, characters, factions, powers, items, quests, and story.
- No vampire-specific dependency is required by the engine.
- No one-to-one recreation of the reference system UI.
- Character progression is designed around authored state, relationship axes, knowledge, and choice consequences rather than only level gain.
- Hidden information is first-class state so private conversations and leaks can change later content.
- Runtime behavior remains deterministic and testable; generative AI is not a gameplay dependency.
