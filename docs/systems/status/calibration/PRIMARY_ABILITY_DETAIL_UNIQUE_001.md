## ABILITY_UNQ_001 — Origin Key

### Identity
- rarity: **Unique**
- family: `system`
- scarcity rule: **1/1 in the universe for this ability identity**
- version: `0.1-calibration`
- design status: `CALIBRATION_PROPOSAL`
- canon status: `NOT_CANON_UNTIL_PROMOTED`
- implementation status: `NOT_IMPLEMENTED`

### Core law
Authenticates the user against one otherwise inaccessible layer of Status architecture, allowing inspection of or access to dormant system functions **only when those functions' own conditions are already satisfied**.

The ability is an authentication/access identity, not unrestricted administrative control.

### Unique ontology
The rarity standard requires explicit answers before canon promotion.

Current calibration answers:
- only one active `Origin Key` identity may exist at a time;
- the exact mechanism enforcing exclusivity is `TBD`;
- transfer on death is `TBD`;
- reappearance after death is `TBD`;
- inheritance is not assumed;
- copying is not assumed possible;
- simulations/imitations do not become the Unique identity merely by reproducing an effect;
- derived techniques may exist only inside the user's own Origin Key law;
- Level-100 replacement interaction remains unresolved by the Level-100 exception standard.

These are intentional blockers, not invitations for implementation guesses.

### What authentication means
A successful use requires:
1. a real Status/system layer or dormant function exists;
2. that layer accepts the Origin Key identity as a valid authentication class;
3. any separate prerequisites for the dormant function are independently satisfied;
4. the user has sufficient Focus/Resolve/system-strain capacity;
5. the layer's safeguards allow the requested inspection/opening.

Origin Key does not make false prerequisites true.

### Hard boundaries
- no unrestricted rule editing;
- no automatic power copying;
- no omniscience;
- no automatic access to every Status layer;
- no bypass of every safeguard;
- no creation of dormant functions that do not exist;
- no assumption that authentication grants write permission;
- inspection and opening are distinct actions;
- a system layer may expose metadata without exposing hidden contents;
- inaccessible/unknown safeguards may reject, limit, delay, or condition access according to future Status architecture;
- exact accessible layers remain `TBD`.

### Prime Legendary boundary
Compared with `ABILITY_PRL_001 Law Silence`:
- Law Silence acts on one modeled interaction rule inside a bounded field;
- Origin Key interacts with Status architecture through authentication.

Origin Key is not “stronger Law Silence.” Its Unique status comes from ontological exclusivity and system role rather than guaranteed superior combat output.

### Rarity rationale
Unique because:
- only one Origin Key identity can exist;
- its governing law concerns privileged Status authentication;
- historical/system significance can exceed ordinary strategic rarity;
- access may reveal or activate otherwise dormant system functions.

Unique does not automatically mean best combat ability.

### Attributes / skills
Likely dependencies:
- Intellect for interpretation;
- Will/Resolve for stable system contact;
- Perception for reading exposed information;
- Powers/Technical Systems/Investigation for understanding outputs where applicable.

The ability itself does not automatically explain everything it reveals.

### Resource model
Focus + Resolve + system strain.

Cost may scale with:
- depth of system layer;
- duration of authenticated session;
- amount of information exposed;
- complexity of dormant function;
- safeguard resistance;
- failed/repeated access attempts.

Exact accounting remains `TBD`.

### Mastery
1. recognize a valid dormant-system access point;
2. authenticate to one permitted layer;
3. inspect limited metadata;
4. distinguish inspection from activation;
5. satisfy and verify child-function prerequisites;
6. open one authorized dormant function;
7. advanced mastery: navigate multiple approved sublayers without gaining unrestricted authority.

Mastery expands reliability and understood access paths, not permission to rewrite the system.

### Techniques
Techniques may:
- identify whether a system endpoint exists;
- stabilize authentication;
- inspect permitted metadata;
- open an eligible dormant function;
- recover from rejected access.

Techniques may not:
- fabricate authorization;
- copy arbitrary abilities;
- edit primary-ability records;
- reveal all secrets automatically;
- override Unique/Level-100 rules without dedicated canon.

### Counters / limitations
Primary constraints:
- no valid system endpoint;
- layer does not recognize this access class;
- prerequisites unmet;
- safeguard denial;
- insufficient resources;
- system strain;
- incomplete interpretation;
- permissions limited to inspection rather than activation.

Counterplay is largely architectural rather than combat-oriented.

### Failure modes
- authentication rejected;
- partial metadata only;
- safeguard lockout;
- function remains dormant because child conditions are unmet;
- corrupted or incomplete interpretation by the user;
- system strain;
- access closes before useful action;
- unknown safeguard behavior, which must be authored rather than improvised.

### World consequence
A confirmed Origin Key user could become uniquely important to:
- Status research;
- classified system studies;
- historical investigations;
- institutions seeking dormant functions;
- groups fearing or protecting system-level access.

But the world cannot know the full significance until the Status architecture itself is documented.

### Public / classified knowledge
Default calibration posture:
- public may know the user has a Unique ability if awakening disclosure permits;
- exact function should likely be heavily misunderstood or classified;
- institutions may know only fragments;
- the user may know more than institutions in some areas and less in others;
- false claims of “system administrator” or “all powers unlocked” should be treated as misinformation.

### Death / persistence blocker
Before canon promotion, define exactly what happens if the user dies:
- slot remains occupied by a dead identity;
- ability disappears permanently;
- ability sleeps and may reappear;
- ability transfers under system rule;
- another mechanism.

No default is selected.

### Level-100 blocker
The Level-100 standard leaves unresolved:
- replacing away from a Unique;
- whether the one-per-universe slot reopens;
- replacing into a Unique;
- whether Status can create another Unique identity.

Origin Key cannot be canon-promoted without a compatible answer or an explicit documented deferral accepted by the owner.

### Visual/content requirements
Presentation should emphasize authenticated Status-layer access, not generic omnipotent “hacker” imagery.

UI must clearly distinguish:
- authentication success;
- access scope;
- metadata inspection;
- unmet child prerequisite;
- denied safeguard;
- opened dormant function.

Player-safe UI must not expose hidden system architecture beyond what Origin Key legitimately reveals.
